# Go-Live Issue Analytics

SQL analysis and a command-center dashboard for support tickets from an Epic EHR go-live. The dataset covers a fictional hospital, Northbridge Regional Medical Center: 10 clinical departments, 400+ deployed devices with their Technical Device Readiness (TDR) results, and about 1,700 ServiceNow-style tickets from one week before go-live through day 14.

> **All data is synthetic.** It is generated by `generate_data.py`. The hospital, devices, and tickets are fictional.

![Go-Live Command Center dashboard](docs/dashboard.png)

## Why I built this

I've supported go-lives as a TDR/Deployment and At-The-Elbow consultant, testing hundreds of workstations and printers before launch and then troubleshooting on the floor once the system goes live. Every go-live generates thousands of tickets, but the command center usually only watches the open count. This project asks the questions I wanted answered on the floor:

- When does volume peak, and how does the mix of issues change?
- Does pre-live TDR testing actually predict which devices break?
- How much does floor (ATE) support resolve without escalating?
- Is overnight coverage keeping up?

## Data model

| Table | What it holds |
|---|---|
| `departments` | 10 units in scope (ED, PACU, Main OR, Pre-Op, Med-Surg, ICU, L&D, Pharmacy, Lab, Registration) |
| `workstations` | Every deployed device: WOWs, desktops, label and laser printers, badge tap readers, barcode scanners |
| `tdr_results` | TDR outcome per device: initial pass/fail, failure reason, retest status |
| `sla_targets` | Resolution targets by priority (P1 1h, P2 4h, P3 24h, P4 72h) |
| `tickets` | Incidents with category, priority, department, device, resolver group, at-elbow flag, shift, and timestamps |

Schema: [`sql/schema.sql`](sql/schema.sql)

| # | Question | SQL techniques |

## Findings

**TDR testing predicts go-live problems.** Devices that failed TDR and were never retested averaged **9.1 tickets each** during go-live, more than 6× the rate of devices that passed (1.4). Even devices that passed on retest ran at double the baseline. The single worst device, a PACU laser printer that was never retested, generated 30 tickets on its own. *Recommendation: block go-live sign-off until every failed device is retested.*

**The first 72 hours are a technical problem; week 2 is a training problem.** Printing, login, and hardware made up 66% of tickets in days 1–3 but only 32% in week 2, when workflow questions took over. Staffing should shift from technical support to ATE coaching after day 3.

**ATE keeps the command center from drowning.** Floor support resolved 80% of workflow questions on the spot in about 19 minutes. The same issues took hours once escalated.

**P1 and P2 tickets are missing SLA.** Only 61% of P1s met the 1-hour target and 68% of P2s met 4 hours, while P3/P4 met 88–92%. The most urgent tickets are the ones falling behind.

**Overnight coverage is thin.** At every priority, night-shift tickets waited about twice as long for a first response and took longer to resolve. P2s averaged about 5 hours overnight vs 3 hours on days.

**Each unit has a distinct day-1 problem.** The ED's top issue was login context (wrong department), Pharmacy's was orders not reaching the dispensing cabinet (interface), and the Lab and PACU were dominated by printer mapping. That's a staffing map for the next go-live.

## Run it yourself

Requires only Python 3.8+ (uses the built-in `sqlite3`; no installs).

```bash
python generate_data.py     # synthetic CSVs in data/
python build_database.py    # load into golive.db
python run_queries.py       # run all queries, save results/*.csv
python build_dashboard.py   # write dashboard/index.html
```

### Write your own queries

```bash
python query.py                                         # interactive SQL prompt
python query.py "SELECT category, COUNT(*) FROM tickets GROUP BY category"
python query.py queries/05_tdr_vs_golive_tickets.sql
```

At the prompt, end each query with `;`. Use `.tables`, `.schema tickets`, `.save out.csv`, and `.quit`. For a visual browser, open `golive.db` in [DB Browser for SQLite](https://sqlitebrowser.org/) (free).

**Practice questions:**
1. Which reporter role (RN, MD, Pharmacist...) opened the most tickets on go-live day 1?
2. What is the average first-response time per resolver group?
3. Which device type had the highest TDR failure rate?
4. Which hour of the day had the most tickets during days 1–3?
5. How many tickets were still open at the end of day 14, by category?

Open `dashboard/index.html` in a browser. It supports light and dark mode and works on mobile.
